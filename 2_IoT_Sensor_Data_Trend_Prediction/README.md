# IoT Sensor Data Trend Prediction

## 1. What the dataset is about and what we're trying to predict
This dataset comes from Microsoft, and it's built to simulate something real factories deal with every day: keeping machines running without surprise breakdowns. It tracks 100 industrial machines over the course of a full year (2015), recording hourly readings like voltage, rotation speed, pressure, and vibration. On top of that, it logs error events, records of when parts were swapped out, and actual failure events across four different machine components. Worth being upfront about. This is a simulated dataset Microsoft built for teaching purposes, not raw factory floor data. That's completely normal for a learning project like this and doesn't make the exercise any less valid.
So what are we actually predicting? For every machine, every hour, the question is simple: is this machine going to break down in the next 24 hours, yes or no? We deliberately didn't try to predict the actual sensor readings going forward, because breakdowns don't follow a smooth pattern, they happen suddenly. And we picked a 24-hour window on purpose: any shorter, and a maintenance team wouldn't have enough warning to actually do anything about it. Any longer, and the prediction gets too vague to trust.

## 2. Why we cleaned the data and built features the way we did
The first surprise was that the data turned out to be clean already, no missing hours, no blank values, no duplicate entries. We double-checked this carefully by lining up every machine's readings against a complete hourly timeline and confirming there were no gaps. Even though we didn't need to fix anything here, we still built in logic to handle small gaps (filling in up to 3 missing hours), because in the real world, sensor feeds are rarely this perfect, and the pipeline should be ready for that.
We also found a small number of unusual readings, less than half a percent of the data. Instead of deleting them, we kept them. Here's why: these unusual spikes are often exactly the kind of stress signal that shows up right before a machine fails. Removing them would mean throwing away the very thing we're trying to detect. So instead, we flagged them as a separate feature and let the model decide how much weight to give them.
For the features themselves, we leaned heavily on rolling 24-hour trends averages, highs, lows for each sensor, rather than just looking at single readings. A single hourly reading is noisy and doesn't tell you much on its own. But if a machine's readings have been climbing steadily over the past day, that's a real warning sign. We matched this 24-hour window to our prediction window so the two line up logically. We did the same thing with error codes, tracking how often they clustered together over time. But the single most useful feature, by far, turned out to be simply: how long has it been since this part was last replaced? That made intuitive sense too machines wear out with use, they don't fail at random.

## 3. Which model we picked and how we stopped it from cheating
We went with LightGBM, a tree-based model, instead of something like an LSTM or a Transformer that's built for sequences. The reason is that by the time we finished building our features, all the time-based patterns were already baked into the data as flat numbers so there was no longer a real need for a model built specifically to understand sequences. LightGBM handles this kind of structured, table-style data extremely well, trains quickly, and makes it easy to see which features actually matter.
To make sure the model wasn't just memorizing or cheating, we took three precautions. First, we split the data by time training on everything before October 2015 and testing only on October through December. This matters a lot, because if we'd split randomly, the model could accidentally peek at future data during training, which would make it look smarter than it really is. Second, instead of telling the model to build a fixed number of trees, we let it stop on its own once it stopped improving — it landed naturally at 130 trees. Third, since actual failures only made up about 2% of the data, we adjusted how much weight the model gave to failure cases, so it wouldn't just take the easy route and predict "no failure" every single time.
The final results came out very strong almost perfect which honestly tracks with this being a simulated dataset designed to have learnable patterns. And when we checked which features the model actually relied on most, it lined up with what makes real-world sense: how long since the last repair, and how sensor readings have been trending both signs you'd expect a human engineer to watch for too.
